# The sallyport protocol

Protocol string `sallyport/0.1`. Receipt schema version `1`.

This document is normative. "Must" and "never" describe behavior sallyport
enforces and its test suite proves. A release that violates any statement here
must fail closed rather than continue.

## 1. Scope

### Supported in v0.1.0

- GitHub Actions, GitHub-hosted Linux runners, public GitHub repositories, and
  public npm packages.
- npm with `package-lock.json`; one root package per repository.
- Stable and prerelease SemVer, with tags exactly matching
  `v<package-version>`.
- npm trusted publishing with OIDC, restricted to stage-only publishing.
- Human 2FA approval, npm provenance, and registry-signature verification.
- Immutable GitHub Releases, optional required signed tags, and committed
  release notes.

### Deliberately not supported

- npm workspaces and multi-package releases; private npm packages; private npm
  dependencies.
- Registries other than npm; pnpm, Yarn, Bun, or JSR; self-hosted runners.
- Automated repository-settings mutation; arbitrary workflow customization.
- Custom publishing shell commands; multiple packages from one tag;
  conventional-commit changelog generation.

Trusted publishing requires a supported cloud-hosted runner; self-hosted
runners are unsupported. The local CLI supports Node `22.18.0` and newer.
Credential-bearing release jobs use exactly Node `24.19.0` and npm `11.17.0`.
npm's lower staged-publishing floor, Node `22.14` with npm `11.15`, is not a
qualified sallyport workflow toolchain.

## 2. The consumer repository contract

A consumer repository contains only these sallyport-relevant files:

```text
.github/workflows/sallyport.yml
package.json
package-lock.json
docs/releases/v<version>.md
etc/release-signing-key.asc       # strict profile only
```

and two npm scripts: `release:check` and `release:smoke`.

### `release:check`

Runs against the tagged source tree. The script must:

- install and test the package, and run type checks, linting, architecture
  checks, coverage, and source-level tests;
- produce the final publishable build output;
- exit nonzero on any failure.

The script must require no credentials or secrets. It must never publish or
stage anything, and must never modify package versions. It must never depend
on npm lifecycle hooks running during the final pack, because sallyport packs
with `--ignore-scripts`.

sallyport runs:

```sh
npm ci
npm run release:check
```

sallyport then performs the one release pack:

```sh
npm pack --ignore-scripts --json --pack-destination "$RUNNER_TEMP/sallyport"
```

The release candidate is packed exactly once. Because package code ran in that
job, the bytes become authoritative only after the fresh `seal` job inspects
and hashes the downloaded artifact.

### `release:smoke`

sallyport runs `npm run release:smoke` with the exact candidate identified by
environment variables:

```text
SALLYPORT_TARBALL=/absolute/path/package.tgz
SALLYPORT_PACKAGE=smoque
SALLYPORT_VERSION=0.1.2
SALLYPORT_DIST_TAG=latest
```

The script must:

- install `SALLYPORT_TARBALL` into an isolated fixture, using
  `--ignore-scripts`;
- verify package exports, types, CLI behavior, or other package-specific
  contracts.

The script must never repack the repository, never publish, and never modify
the supplied tarball. sallyport provides a copy of the tarball and verifies that
copy's hash afterward. This is the only package-specific part of the release
system.

## 3. The generated caller workflow

Each consumer gets exactly one generated file,
`.github/workflows/sallyport.yml`:

```yaml
# Generated by sallyport. Update with `npx sallyport init --upgrade`.
name: sallyport

on:
  push:
    tags:
      - 'v*'
  workflow_dispatch:
    inputs:
      candidate_run_id:
        description: Successful staging workflow run ID
        required: true
        type: string

permissions: {}

concurrency:
  group: sallyport-${{ github.repository }}
  cancel-in-progress: false

jobs:
  stage:
    if: github.event_name == 'push'
    permissions:
      actions: read
      contents: read
      id-token: write
    uses: zsumz/sallyport/.github/workflows/stage.yml@0123456789abcdef0123456789abcdef01234567
    with:
      profile: strict
      signer_fingerprint: ${{ vars.SALLYPORT_SIGNER_FINGERPRINT }}

  finalize:
    if: github.event_name == 'workflow_dispatch'
    permissions:
      actions: read
      contents: write
    uses: zsumz/sallyport/.github/workflows/finalize.yml@0123456789abcdef0123456789abcdef01234567
    with:
      candidate_run_id: ${{ inputs.candidate_run_id }}
      profile: strict
      signer_fingerprint: ${{ vars.SALLYPORT_SIGNER_FINGERPRINT }}
```

Required properties:

- Both reusable workflows must use the same full 40-character commit SHA.
- The caller must never use `secrets: inherit`, and must never carry an npm
  token.
- Stage and finalize must never run concurrently, and a release job must never
  be canceled halfway through.
- The caller grants the maximum permission set. Jobs inside the reusable
  workflows reduce it further; a called workflow can never elevate beyond what
  its caller granted.
- The package name, version, access, repository, and dist-tag must be derived,
  never supplied by arbitrary workflow inputs.

npm validates the **calling** workflow filename when reusable workflows are
involved: the npm trusted publisher must be configured for `sallyport.yml`,
not `stage.yml`. npm requires `id-token: write` in both the caller and the
reusable workflow.

## 4. Profiles

### Standard

- The tag must exactly match `v<package-version>`.
- The tag commit must be reachable from the repository's default branch.
- `package.json` and `package-lock.json` must agree.
- Repository metadata must match the GitHub repository.
- Committed release notes must exist.

### Strict

Everything in standard, plus:

- The tag must be annotated and carry a valid OpenPGP signature.
- The signature fingerprint must match the repository variable
  `SALLYPORT_SIGNER_FINGERPRINT`.
- The imported public key must be `etc/release-signing-key.asc`.
- Release notes must be `docs/releases/v<version>.md`.

There is no separate signer name or email check. The cryptographic fingerprint
is the authorization boundary.

## 5. Dist-tag policy

The consumer never supplies a raw publishing tag. sallyport derives it from the
version:

```text
1.4.0          → latest
1.4.0-alpha.2  → alpha
1.4.0-beta.1   → beta
1.4.0-rc.3     → rc
```

Rules:

- Stable versions always use `latest`.
- Prerelease versions use the first prerelease identifier.
- The first prerelease identifier must be a nonnumeric, valid npm dist-tag:
  lowercase, starting with a letter, containing only letters, digits, and
  hyphens.
- sallyport must reject ambiguous forms such as `1.0.0-1`, identifiers that
  parse as version ranges (`v2`, `1e5`, `x`), and the reserved identifier
  `latest` — a prerelease must never move `latest`.
- Versions carrying build metadata (`1.0.0+build`) are not releasable.
- The staged package's dist-tag is recorded in the candidate receipt.
- Finalization must verify that the public dist-tag points to the exact
  version.

## 6. Stage flow — `stage.yml`

Three jobs:

```text
prepare ─────> seal ─────> stage
package code    clean        npm OIDC
no authority    receipt      no package code
```

### Job 1: `prepare`

Permissions: `contents: read` only. No OIDC. No write access.

**Step A — validate the invocation.** The event must be `push`, the ref must
be a tag, the tag must equal `v<package-version>`, the repository must match
`package.json` `repository`, the package must be public, the repository must
contain one root package, and `package-lock.json` must be present. The tag
must resolve to the event commit and be reachable from the exact default branch
ref fetched into `refs/sallyport/default-branch`. In strict mode, the annotated
signed tag and expected fingerprint must verify.

**Step B — check out both repositories.** The consumer is checked out at its
exact tag with `persist-credentials: false` and `fetch-depth: 0`. sallyport
is checked out into a separate directory at the exact reusable-workflow commit
derived from the `github.workflow_ref` and workflow SHA context:

```text
$GITHUB_WORKSPACE/consumer
$GITHUB_WORKSPACE/sallyport
```

Only unprivileged jobs ever check out sallyport implementation code.

**Step C — establish the qualified toolchain.** sallyport v0.1.0 pins the
`ubuntu-24.04` runner family, exact `actions/*` commit SHAs, Node `24.19.0`,
and the npm bundled with it, `11.17.0`. It then asserts the observed
`node --version` and `npm --version`. There must be no `24.x` range, no
`npm@latest`, and no runtime global npm upgrade in the credential-bearing job.
The pinned versions exceed npm's staged-publishing floor; that floor is not an
alternative supported workflow toolchain.

**Step D — verify package metadata.** The package name must exist; `private`
must not be `true`; the version must be valid SemVer; the tag must be exactly
`v${version}`; `publishConfig.access` must be public or the package must be
unscoped and public; `publishConfig.provenance` must not be explicitly
disabled; `repository.url` must exactly identify the caller repository; the
lockfile name and version must agree with `package.json` at both the top level
and the root entry; the registry must not already contain the version; and the
required release notes must exist.

**Step E — run repository validation.** `npm ci`, then
`npm run release:check`. No secrets are present.

**Step F — pack once.** `npm pack --ignore-scripts --json`, renaming the
artifact to the fixed safe name `package.tgz`. This is an untrusted byte output;
the fresh `seal` job performs the authoritative manifest inspection and digest.

**Step G — smoke the emitted candidate.** sallyport copies
`package.tgz → smoke-package.tgz`, sets the `SALLYPORT_*` environment
contract, runs `npm run release:smoke`, and verifies by hash that the copy was
not modified during the smoke. This is useful package behavior evidence, not a
trusted assertion about the bytes; only `seal` can make them authoritative.

`prepare` uploads only `package.tgz`. Its artifact ID, not its name, is handed
to the next job. No metadata written by package code is trusted.

### Job 2: `seal`

Permissions: `actions: read`, `contents: read`. Fresh runner. No OIDC, package
install, package script, or consumer code.

`seal` downloads the tarball by immutable artifact ID, checks out the event
commit and pinned sallyport implementation from scratch, fetches the tag and
default branch into private refs, and repeats source, ancestry, commit, and
signature verification. It inspects `package/package.json` inside the tarball
and compares it with the exact source commit. Only then does it produce the
authoritative candidate receipt (`candidate.json`):

```json
{
  "schema": 1,
  "protocol": "sallyport/0.1",
  "sallyport": { "version": "0.1.0", "workflow": "zsumz/sallyport/.github/workflows/stage.yml", "sha": "<40-hex>" },
  "repository": { "name": "zsumz/smoque", "id": 1286348597, "defaultBranch": "main" },
  "source": { "tag": "v0.1.2", "commit": "<40-hex>", "signed": true, "signerFingerprint": "B58439871CD2A7275B20CC19EC8E4D26598A0373" },
  "package": { "name": "smoque", "version": "0.1.2", "access": "public", "distTag": "latest" },
  "tarball": { "filename": "package.tgz", "bytes": 123456, "sha256": "...", "sha512": "...", "integrity": "sha512-..." },
  "run": { "id": 123456789, "attempt": 1 }
}
```

The sealed artifact is named
`sallyport-candidate-<tag-commit-sha>-<run-attempt>`, contains exactly
`package.tgz` and `candidate.json`, and is retained for 90 days. Its immutable
artifact ID is handed to `stage`.

### Job 3: `stage`

Permissions: `id-token: write`. Environment: `npm-stage`.

This job has no caller checkout, no sallyport checkout, no `npm ci`, no package
scripts, no local Actions, no cache, no inherited secrets, no npm token, no
repository write permission, and no shell command assembled from unvalidated
package values.

It downloads only the sealed artifact ID. Embedded dependency-free Node code
recomputes the tarball digest and independently binds repository name and ID,
default branch, tag, commit, run ID and attempt, workflow SHA, profile, signer,
version, and derived dist-tag to trusted GitHub context. It then invokes:

```text
npm stage publish package.tgz --tag <validated-dist-tag> --access public --ignore-scripts --provenance --json
```

It then parses and records the returned stage ID.

The stage summary reports package@version, dist-tag, candidate SHA, stage ID,
candidate run ID, and signer, plus the next commands: `npm stage view`,
`npm stage download`, `npm stage approve`, and
`gh workflow run sallyport.yml -f candidate_run_id=<run-id>`.

## 7. Human approval

The approver can inspect the exact bytes before anything becomes public:

```sh
npm stage view <stage-id>
npm stage download <stage-id>
npm stage approve <stage-id>
```

The downloaded SHA-256 must equal `tarball.sha256` in `candidate.json`.
Approval requires 2FA. OIDC credentials can never approve or reject a stage.

```text
CI may prepare and stage.
Only the maintainer may make it public.
```

## 8. Finalize flow — `finalize.yml`

Three jobs:

```text
verify_core ─────┬────> release
clean + sealed   │      GitHub contents write
                 │      no package code
public_smoke ────┘
package code; no trusted outputs
```

The workflow receives only `candidate_run_id`, `profile`, and
`signer_fingerprint`. Everything else must derive from the candidate receipt.

### Job 1: `verify_core`

Permissions: `actions: read`, `contents: read`. No OIDC. No write access.

**Step A — retrieve the exact candidate.** Using the explicit run ID, verify
that the run belongs to the current repository; that it used
`.github/workflows/sallyport.yml`; that its event was a tag push; that it
completed successfully; that the candidate artifact is present; that the
candidate's reusable-workflow SHA equals the currently pinned finalizer SHA;
that the repository ID matches; and that the tag and commit match the receipt.

**Step B — reverify source identity.** Check out the receipt's exact commit
with `persist-credentials: false`, fetch the tag separately, require its peeled
target to equal that commit, and repeat default-branch ancestry, release-note,
and strict signature verification against private refs.

**Step C — wait for npm registry convergence.** Only temporary states may be
retried: version not yet visible, dist-tag not yet visible, tarball
temporarily unavailable. A cryptographic or metadata mismatch must never be
retried. The retry budget is 30 attempts at a 10-second interval, bounded by
5 minutes.

**Step D — verify the public package.** The exact version must exist; the
expected dist-tag must point to it; the registry `dist.integrity` must match
the candidate; the tarball must download; the public SHA-256, SHA-512, and
byte length must equal the candidate's; the packed manifest must match name
and version; the registry signature must be valid; and an npm provenance
attestation must exist and identify the expected GitHub repository and
workflow run.

**Step E — seal the release bundle.** Before any consumer dependency or script
runs, build and upload `package.tgz`, `candidate.json`, `release.json`,
`SHA256SUMS`, and `RELEASE_NOTES.md`. Every file except the checksum file is
listed in `SHA256SUMS`; the immutable bundle artifact ID is a job output.

`release.json`:

```json
{
  "schema": 1,
  "protocol": "sallyport/0.1",
  "candidateReceiptSha256": "...",
  "releaseNotesSha256": "...",
  "package": { "name": "smoque", "version": "0.1.2", "distTag": "latest" },
  "candidate": { "sha256": "...", "sha512": "..." },
  "registry": { "sha256": "...", "sha512": "...", "integrityVerified": true, "signatureVerified": true, "provenanceVerified": true },
  "source": { "repository": "zsumz/smoque", "tag": "v0.1.2", "commit": "..." }
}
```

### Job 2: `public_smoke`

Permissions: `actions: read`, `contents: read`. No OIDC or write access.

This separate job downloads the sealed bundle by artifact ID, checks out the
exact consumer commit, installs dependencies, and runs `release:smoke` against
a copy of the sealed public bytes. It uploads no artifact and exposes no output;
the release job consumes only its success status.

### Job 3: `release`

Permissions: `actions: read`, `contents: write`. Environment: `github-release`.

This job has no repository checkout, no dependency installation, no caller
code, no package script, no OIDC, no npm access, and no arbitrary release
command.

It downloads the exact bundle artifact ID from `verify_core`, resolves the
originating sealed-candidate artifact from the candidate run, downloads that
artifact by ID, and requires byte-for-byte receipt and tarball equality. It
then rechecks every hash and independently binds the run, attempt, repository,
workflow, workflow SHA, tag, commit, profile, and signer to GitHub context. It
re-peels the tag immediately before each write, then publishes draft-first:

1. Create a draft GitHub Release for the existing tag.
2. Add the committed release notes.
3. Attach `package.tgz`, `candidate.json`, `release.json`,
   `RELEASE_NOTES.md`, and `SHA256SUMS`.
4. Publish the draft.

Immutable releases fix assets and the tag at publication, so the draft-first
order is required rather than cosmetic.

## 9. Replay behavior

| Existing GitHub state         | Result                               |
| ----------------------------- | ------------------------------------ |
| No release                    | Create draft, attach assets, publish |
| Matching draft                | Resume draft and publish             |
| Matching published release    | Successful no-op                     |
| Same tag, different receipt   | Hard failure                         |
| Same tag, different assets    | Hard failure                         |
| Same tag, different title     | Hard failure                         |
| Same tag, different notes     | Hard failure                         |
| npm package missing           | Fail without writing                 |
| npm bytes differ              | Critical failure                     |
| Provenance missing or invalid | Fail without writing                 |

npm approval can succeed while GitHub is down. The finalizer may be rerun
later; it must never republish the npm version, and it must never silently
overwrite a conflicting GitHub Release. See [recovery](./recovery.md).

## 10. Security invariants

1. No persistent npm publishing token — CI uses only short-lived OIDC
   credentials.
2. Package code never runs with npm publishing authority. `prepare` runs
   package code and has no OIDC; `stage` has OIDC and runs no package code.
3. Package code never runs with GitHub Release write authority. `public_smoke`
   runs package code and exports no trusted output; `release` can write and
   runs no package code.
4. One authoritative tarball — packed once, sealed on a fresh runner, staged,
   downloaded again from the public registry, and compared byte for byte.
5. CI may stage but may never publish directly; the trusted publisher is
   restricted to `--allow-stage-publish`.
6. Human approval is unavoidable, and requires 2FA.
7. Central code is immutable per consumer, pinned by the full implementation
   checkpoint SHA; CI rejects runtime changes above that checkpoint.
8. Release metadata is derived, never supplied by workflow inputs.
9. External actions are immutable, pinned by full commit SHA.
10. Public bytes are independently verified before any GitHub Release is
    written.

See [threat model](./threat-model.md) for what these invariants do and do not
cover.
